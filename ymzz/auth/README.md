# Website account service — reference

English | [中文](README.zh.md)

This private, independently installed Node.js 24.15+ service implements website accounts using Better Auth (MIT), Nodemailer (MIT-0), and built-in SQLite. GitHub Pages remains public, static, and usable without an account. It cannot execute this backend. No hosted auth subscription, wallet, payment service, or desktop-agent identity is introduced. Hosting and SMTP are not provided by the repository; use an existing TLS-capable Node host and existing mail service if available. Free operation depends on those existing resources and their quotas; no universal free production hosting is claimed.

## Authentication and security

`/account` provides Google authorization-code sign-in (state + S256 PKCE, explicit signed ID-token validation for issuer, audience and expiry), five-minute one-use hashed email OTP sign-in/verification, authenticator TOTP enrollment with confirmation, ten encrypted one-use recovery codes, and sign-out. It uses a Google button, not automatic Google One Tap or Google's browser SDK. Basic identity scopes only; no Gmail/Drive permissions. Google requires a verified email. Matching email never silently links accounts: sign in first, then explicitly link the same-email Google account.

Every fresh Google or email-OTP session belonging to a TOTP-enabled user is **server-restricted** until TOTP or a recovery code passes. Better Auth does not enforce its credential-login 2FA hook on passwordless methods by default; `app.mjs` therefore checks a separate server-side, session-specific assurance record on every account and management request. The provider handler must never be exposed directly. `/api/account` is the only identity/business-data endpoint; future protected routes must use the same assurance check. There is no API proxy into the local agent. Raw session APIs and unused provider routes are denied. Authenticator enrollment invalidates old assurances. Disabling 2FA requires an already verified session.

Sessions last at most 12 hours, use host-only Secure/HttpOnly/SameSite=Lax cookies in production, and are never stored in browser storage or JSON tokens. Mutations require the exact Origin and JSON content type. There is no cross-origin session API. OTP/factor attempts have shared SQLite rate limits by IP and by account/address; TOTP reuse within 90 seconds is rejected across sessions. A global send budget defaults to 100 emails per hour (`MAIL_HOURLY_LIMIT`, configurable from 1 to 10000); failed delivery also consumes budget. Mail errors and auth failures expose generic responses. No request bodies, OTPs, callback queries, tokens, or personal data are logged. SMTP uses certificate-validated TLS or mandatory STARTTLS. Mail delivery is awaited, not faked.

## Deployment tutorial

1. Choose the **actual HTTPS account origin and existing persistent Node host** before deployment; the account origin can be separate from GitHub Pages, but account UI and account APIs must share one origin. No backend origin has been selected or provisioned. This service does not run on Cloudflare Workers unchanged; a Workers/D1 adapter is a separate deployment decision.
2. Run `npm ci --prefix ymzz/auth --ignore-scripts`. Review `.env.example`; set variables through the host's secret manager, not site JavaScript or a committed file. Google and SMTP are independently disabled unless their complete configuration exists. Production startup rejects insecure origins, weak/missing secrets, and partial provider configuration.
3. Register a Google **Web application** OAuth client with redirect URI `<AUTH_ORIGIN>/api/auth/callback/google`. Configure the consent screen, testing/publishing status, authorized domains, privacy terms and permitted test users in the owner's Google project. No Google forms are submitted by this code. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` only on the backend.
4. Configure an existing SMTP sender with permitted transactional delivery and its required SPF/DKIM/DMARC records. Set `SMTP_HOST`, `SMTP_PORT` (465 or 587), `SMTP_USER`, `SMTP_PASSWORD`, and `MAIL_FROM`. Never use an open relay or put credentials into the browser.
5. Set `AUTH_ORIGIN`, independent random `AUTH_SECRET` (at least 32 characters), `AUTH_DATABASE` outside the web root, and `PORT`. Back up existing SQLite/WAL files consistently and preserve the encryption secret; key loss makes encrypted TOTP secrets and OAuth tokens unreadable. Run `npm --prefix ymzz/auth run migrate`, `npm --prefix ymzz/auth run build`, then `npm --prefix ymzz/auth start`. Migrations are explicit, never run on HTTP requests. Run one Node instance per SQLite database on durable local storage, not ephemeral/serverless disks or a network share.
6. Terminate HTTPS in an existing local reverse proxy and forward to `127.0.0.1:3100`. Bind no public Node port. Set `TRUST_PROXY=loopback` only when that proxy **overwrites** `X-Real-IP` with the client's single IP; otherwise leave unset (all requests share the proxy IP limit). Apply edge/IP/global mail abuse limits and service quotas before public signup. Keep the account database, backups and secret manager private. Retention/deletion, monitoring, backup restoration and SMTP quotas are operator responsibilities.
7. Perform owner-authorized real Google login, email delivery, enrollment, logout/new-browser TOTP/recovery, throttling, backup/restore and browser tests at the real domain. Until those pass, keep `ymzz/site/config.js` `accountUrl` empty: no login link or outbound auth request is exposed on the public site. Only then set it to `<AUTH_ORIGIN>/account`; it is navigation, not a CORS API connection. Do not claim that repository tests enable production login.

## Local validation

`npm --prefix ymzz/auth run build && npm --prefix ymzz/auth test` runs synthetic signed Google provider fixtures, in-memory SQLite, and an intercepted mail callback; it sends no email and never contacts Google. `node ymzz/scripts/check-site.mjs` validates the unchanged public-site layout/resources. For local manual inspection use `NODE_ENV=development`, a loopback `AUTH_ORIGIN`, an independent local `AUTH_SECRET`, and a temporary private database; missing providers remain disabled. Never enable development mode in production.

Dependency versions/integrities are pinned in the separate `package-lock.json`; the monorepo runtime/desktop dependency graph is unaffected. Preserve the dependencies' bundled license notices when distributing the service; those licenses allow commercial use. Google, SMTP, and hosting terms still apply independently.
